# Geld — guide for agents and contributors

Geld is a browser extension that hides test files (and, optionally, other review noise) from GitHub diffs. This repository is a pnpm monorepo that also hosts the marketing site for geld.sh. Read this file before changing anything; it captures decisions that are not obvious from the code.

## Layout

```
packages/core/       @geld/core — pure TypeScript, no browser APIs. Glob matcher, hidden-file
                     categories & patterns, repository rules, settings model, unified-diff parser,
                     number formatting. Unit tested with Vitest. Consumed as TS source via
                     package.json "exports" (no build step).
packages/review/     @geld/review — pure TypeScript, no browser/Node APIs. PR summary payload
                     (GeldPrMeta), clustering, bot registry, comment render/parse, optional
                     OpenAI-compatible client. Shared by the Action and the extension.
packages/github/     @geld/github — pure TypeScript, no browser APIs. Geld GitHub App user
                     authorization (device flow, web flow, token-refresh coordinator, revoke) and,
                     to come, the API clients behind the dashboard. Packaged like core.
apps/extension/      @geld/extension — the WXT extension (Chrome, Edge, Firefox, Safari).
apps/action/         @geld/action — GitHub Action that upserts one review-summary comment per PR
                     (`pull_request_target`, GraphQL, never checks out PR code). `dist/` is a
                     committed esbuild bundle; Actions require built JS.
apps/site/           @geld/site — Next.js site for geld.sh (see "Website" below).
assets/brand/        Logo + logomark SVGs (black and white variants). Both apps reference these.
.github/workflows/   CI: `pnpm check` (typecheck + tests everywhere), `pnpm catalog:check` (generated
                     catalog and its signature are current) and `pnpm zip:all` artifacts.
catalog/             patterns.json + patterns.sig: the signed pattern catalog installed extensions
                     fetch. Generated from core — never edit by hand (see "pattern catalog" below).
scripts/             catalog-build.ts (generate/check), catalog-sign.mjs, catalog-keygen.mjs.
.cursor/plans/       Plan documents for larger pieces of work.
.cursor/ideas/       Parked ideas, one file each (status, why, why not yet, how), so a thought not acted
                     on now is easy to find later. Current: a Security row beside Reports; a person's
                     top-level comment that is waiting on the reader (needs-reply items for comments);
                     a Review tab that walks a PR in AI-planned steps with an assistant beside it;
                     a Scope map of what a PR or its stack touches in the repository.
```

Store publishing (`.github/workflows/publish.yml`) runs after every CI release on `main`, every six hours and on demand: it submits the latest release to Chrome, Edge, Firefox and Safari, skipping a store that already has that version or has a submission under review (Chrome/Edge cannot cancel reviews via API; Apple can and the Safari job withdraws a waiting submission). The pattern catalog is signed and committed by CI on push (`GELD_CATALOG_PRIVATE_KEY` to sign, `CATALOG_DEPLOY_KEY` — a write deploy key — to push, with "Deploy keys" on the ruleset bypass list). Zips built by CI carry a four-part version (`package.json` version + run number, via `GELD_BUILD_NUMBER` in `wxt.config.ts`), so no bump commit is needed between store releases. Credentials and listing assets: `apps/extension/store/PUBLISHING.md`.

Releases: every push to `main` that touches the extension (apps/extension, apps/action, packages/core, packages/review, assets/brand, the lockfile, or the workflow) publishes a GitHub Release from CI, tagged `v{version}-build.{run}` with one zip per browser plus `-sources.zip` for Firefox review, auto-generated notes (editable afterwards) and marked latest; the site's install buttons read `/releases/latest`. Bump `apps/extension/package.json` `version` for a new version number; the build number keeps tags unique. `workflow_dispatch` forces a release.

Commands (root): `pnpm check` (typecheck + tests for core and the extension, lint + production build of the site, and `catalog:check`), `pnpm test`, `pnpm build`, `pnpm zip:all` (zips for all four browsers into `apps/extension/.output/`), `pnpm dev` (extension; it does **not** launch a browser — load `apps/extension/.output/chrome-mv3-dev` once with "Load unpacked" in your own Chrome, or `firefox-mv2-dev` via about:debugging, and WXT rebuilds and reloads it on change; a git-ignored `apps/extension/web-ext.config.ts` with `disabled: false` brings the launcher back per developer), `pnpm dev:site`.

## Conventions

- TypeScript strict everywhere. **Never use `any`**, explicitly or implicitly, and never `ZodTypeAny`. Prefer type guards and `unknown` over casts; the codebase has no `as X` casts outside a couple of well-commented interop shims. Keep it that way.
- Extension imports shared logic only from `@geld/core` (never `../../packages/core/...`). Anything that could be reused by the site belongs in core; anything touching `browser.*`, the DOM or WXT stays in the extension.
- UI copy is short and specific, with no em or en dashes and no semicolons (a plain sentence break, a comma or a middle dot instead); commit messages explain *why*.
- **Code comments are the exception, not the habit.** Most code should carry none: a comment that only restates what the line plainly does (`// centre on the line`, `// pull in from the gap`) is noise and is not wanted. A comment earns its place only when the code cannot speak for itself — genuinely subtle or ambiguous logic, something load-bearing or sensitive where a wrong change would break non-obvious behaviour, a *why* the reader could not infer (a GitHub quirk worked around, an ordering that matters), or a note tying code that must stay in step with code elsewhere (mirrored constants, a shape shared across packages). Keep it to a single line; reserve a longer, several-line comment for those same situations when one line truly cannot carry it. When in doubt, leave it out and let the names and structure explain. (The existing long design notes in this file and the occasional dense block comment in the content script are the load-bearing kind and stay.)
- Website stack (fixed by the owner): latest stable Next.js (App Router, static generation; Cache Components/PPR for any dynamic bits), Tailwind, **shadcn on base-ui (not Radix)**, the **`cn` package** for class merging (not `clsx`, `tailwind-merge` or `cnfast`). Deployed on Vercel under the **dreamthinkbuild** account to **geld.sh** (canonical `www.geld.sh`, apex redirects).

## How the extension works (short)

- `apps/extension/entrypoints/github.content/` runs on github.com (and user-added GitHub Enterprise hosts). `src/github/controller.ts` is the brain: a debounced `MutationObserver` re-runs an idempotent `apply()` that classifies each diff entry with `@geld/core`'s matcher, hides matches with **CSS flex `order` + attributes** (GitHub's DOM is never moved — the React view breaks otherwise), rewrites header counts, renders the bottom "N files hidden" row, and turns the file-tree sidebar into a full-height accordion ("Essential" — GitHub's own tree, what is left to review — + one panel per hidden category).
- **Category panels lead each file with the icon GitHub's tree shows for it**, never the plain `file` octicon: `file-added` (success), `file-removed` (danger), `file-moved` (attention), `file-diff` (muted) for an edit. The React tree's leading visual is cloned per item (`TreeFileNode.statusIcon`); where the view shows none (classic tree, files GitHub has not rendered) `tree-section.ts` `fileVisual` draws it from `FileStats.status` (`added`/`deleted`/`renamed`/`modified`, parsed from `new file mode` / `deleted file mode` / `rename from` in `diff-parse.ts`; absent in older cache entries → modified). Colours come from Primer's `fgColor-*` utilities on the svg. Folders are `file-directory-open-fill` when expanded and `file-directory-fill` when collapsed (`setDirVisual` swaps them on toggle), as GitHub's are. GitHub's PR tree keys its icons on the change alone — it has no per-file-type icons there (those belong to the repository code tree), so neither do we.
- **PR conversation digest** (`src/github/review/`, `@geld/review`). On the conversation tab the extension looks for one comment by `github-actions[bot]` (or `geld[bot]`) carrying the machine payload in **an empty `<span title='geld:…'>` inside the footer line** (`PAYLOAD_ATTR_PREFIX`, `encodePayloadAttribute`/`PAYLOAD_CARRIER_SELECTOR` in `summary-parse.ts`). GitHub strips HTML comments from the rendered page, so `<!-- -->` cannot carry it; a fenced ```geld block (what older summaries used — still read, never written) showed everyone without the extension a collapsed "Geld data" dump. GitHub's sanitizer keeps `title` on a `span`, an empty inline has no size and so no tooltip, and the footer's own paragraph takes it with no new line: invisible to every reader, in the DOM for the extension (`getAttribute('title')` hands back the decoded JSON). Written single-quoted so JSON's double quotes cost nothing (`&`, `'`, `<`, `>` become entities; double-quoted, a 40 KB payload grew past the 65,536-character comment cap) and `truncateMeta` budgets the encoded size; verified against GitHub's `/markdown` API — the attribute round-trips byte for byte, including quotes, angle brackets, backticks, `@`/`#` sequences. Author + schema + "anchors must exist in the DOM" is the trust boundary; a forged payload is ignored. The Action applies the same author gate when it looks for the comment to update (`findSummaryComment(comments, [tokenLogin])`: `github-actions[bot]`, the Geld Apps, or whatever login the token answers `GET /user` with — the workflow token answers 403 there and writes as `github-actions[bot]`): a participant posting the marker or heading cannot make the Action PATCH a comment it does not own and fail instead of publishing. Fresh `headSha` → render the panel from the payload (zero crawl). Stale/partial/missing → crawler fallback with the same layout, "Updating…" when a summary exists but is behind. **The panel (`review/panel.ts`, `.geld-review`) grows out of the bottom of the description card**: inserted right after the card (`[data-geld-attached]` squares its bottom corners, the panel's top ones are square too, `margin-top: -1px` shares the border), so the two read as one box. Inside it borrows the merge box's checks list: a summary strip (progress meter, needs-reply chip, copy), then **the status rows** (`statusRows`, in triage order: *Reviews*, *Review bots*, *Reports*, *CI checks*, *Previews*; each only when it has something to say — *Review bots*: one outlined pill per bot with the page's icon, name, detail and a traffic-light glyph via `botHealth` (5/5 or clean → green check, 3–4/5 or findings → yellow dot, 1–2/5, high severity or failed → red X); clicking opens the bot's run summary **where the reader is** (`onOpenAnchor`: the fold row in compact view, else the browser's fragment jump); the row's ⟳ menu re-runs one bot or all, with an in-menu confirm, posting one comment per bot in sequence. *CI checks*: the merge box's checks section is located **by its own headings** ("1 in progress check", "8 successful checks" — the nearest ancestor holding all of them), not by container markup, which differs between the Rails and React merge boxes; its counts (`checkCountsFrom`) sit behind a GitHub-style status ring, and **in compact mode the section is folded out of the merge box** (it joins the fold targets under the key `checks`, not shown as a fold row) and shown in the CI row's slot when opened. The section and its original parent are remembered (`checksSectionEl`, `mergeHomeEl`) so counts and the review-requirement text keep reading correctly while the section is away — otherwise the row vanished and flip-flopped. Re-running failing checks needs the checks page or an App, so there is no action for it. *Reviews*: `requiredReviewsFrom` ("At least 2 approving reviews are required", "1 approval") as `1/2 approvals`. Only registered review bots, or logins in `reviewBots`, get a verdict (`reviewBotIdFor`); other `[bot]` accounts — deploy previews, CI — fold but never appear as reviewers), the TL;DR, then a collapsible heading per group ("2 open items ⌄", "1 done item" — collapsed by default — "5 hidden activities") and one line per row: status icon, poster avatar read from the page (round for people, 4px-radius for bots), bold ellipsized title, muted `path · authors · N comments`, a badge pill, and on the right eye (view here) / reply / ⋯ (Resolve or Mark done, Show in timeline, Copy link). **Items are review threads only** (`isReviewItemComment`): top-level comments and review bodies cannot be resolved on GitHub, so a "done" there would come straight back on reload; they stay in the timeline, or fold when they are a bot's run summary or a **review request** (`isTriggerComment`: "@greptileai", "bugbot run", "/devin review" — every registered trigger plus the generic "@handle verb" shape, one per line or several in a row with only whitespace/punctuation between; folded silently — no row, not counted — since the bots' answers are in their rounds and the re-run control posts new ones). **"Request a review" (the ⟳ menu on the Review bots row, `requestMenu` in panel.ts) is a checklist of every registry bot** (`requestableBots` in panel-model.ts): each line has a checkbox, the bot's mark (the page's picture when it has one, else GitHub's for the App: `avatars.githubusercontent.com/in/<appId>` from the registry's `appId`, read from `GET /users/<login>`; `/<login>` serves an identicon for App logins) and what its last run on this PR said (`botRunState`: Failed, Findings, Passed, Running, Earlier commit, Not run, in the chip's colours; failed and stale runs start ticked so the usual case is open, glance, Run). **How a run asked for ends** (`verdictsFrom`, `@geld/review/bots.ts`): a person's trigger comment ("@greptileai", "bugbot run") or the bot's own "Starting…" line puts the bot at `running` until it speaks — a new summary comment, review threads, or its check run's conclusion — and after `STATUS_LINE_STALE_MS` (45 min) of silence with no check to go by the run reads `failed`. Greptile reports a re-run by *editing its existing summary in place* ("Reviews (2)", a new confidence score) and posts nothing new, so `BotComment.editedAt` counts too: a bot summary edited after the ask is the report, with the verdict its words now say. The extension reads that time from GitHub's edit-history log (`edit-times.ts`: the header's `details-menu[src*="show_edit_history_log"]`, first `relative-time` = most recent edit), asked for only on a bot's summary posted before a run that is still waiting on that bot (`runsAskedFor`), once a minute while that is so, never otherwise. Seen on mint#12546: `@greptileai` at 21:46 and 21:54, the summary edited 21:57 from 4/5 to 5/5, no new comment — without the edit the chip would have said running until 22:31. **A bot that acknowledges a trigger says so with a reaction** (`ReviewBot.acknowledges: 'reaction'`, Greptile's 👍 on the trigger comment, verified Oct 2026): the crawl reads each comment's reactors from GitHub's reaction tooltips ("greptile-apps[bot] reacted with thumbs up emoji", `reactorsOf` → `RawComment.reactedBy` → `BotComment.reactedBy`), and a trigger for such a bot that it has not reacted to after `ACK_GRACE_MS` (3 min) was never picked up — it does not start a run, the earlier verdict stands and the reader can ask again (mint#12546's first `@greptileai` got no reaction and no review for half an hour; the second was reacted to within seconds). Bots that start silently keep the 45-minute rule. **A bot that refuses to run is a `failed` verdict with its reason** (`refusalReason` in `bots.ts`: "Skipping Bugbot: Bugbot is disabled for this repository", "not enabled for this repo", "no credits remaining", "could not access the repository", "permission denied" — a sentence or two, shaped like a refusal; "Skipping the test suite…" in a review is not one): the run that was asked for did not happen, so the request stops reading as *running*; but **the chip shows the bot's last real run**: a review the bot made earlier (a summary comment, or the threads a request had set aside — `runsBeforeAsk`) stands, with `reviewedSha` saying whether it is behind the head, and only a bot that never reviewed here gets `{ verdict: 'failed', reason, sourceId: <the refusal comment> }` (`BotVerdictRecord.reason`, optional in the schema). A refusal is read in three shapes only — an explicit `Skipping <Bot>:`, a refusal phrase in a sentence that names the bot / review / `this`-`the`-`your` + repository, account, installation / credits / the reader, or a *bare* refusal (first sentence ≤ 8 words opening on the phrase, only refusal vocabulary after it, optionally ≤ 200 chars of advice with nothing code-like: no code span, path, identifier, or a link into the repository's files) — everything else is a review. **`loading`** is the extension-only verdict for a bot whose only word so far is an old request while the timeline is still being read (`verdictsFrom(…, { partial })` from `timelineIngesting`); whole, the same request reads `failed`. The chip reads "Bugbot skipped" and wears the **warning triangle** (`ICON_ALERT`, amber: health `warn`, not `bad`, since nothing is wrong with the pull request, only the bot's setup, so the Review bots row does not go red for it; a run that broke with no reason, and a low score, stay `bad` with the red X) instead of a verdict's light — nothing was reviewed — and opens the bot's own words (its `sourceId`); its aria-label and hover card say the reason ("Did not review this pull request: Bugbot is disabled for this repository"); the request menu lists it as "Skipped", unticked, since asking again changes nothing until the bot's setup does. A run that broke with no words stays "failed" with the same triangle. **Rerun on a bot's run summary** (`ChatByline.rerun`, `rerunControl` in chat.ts, `withRerun` in overview.ts): the one-bubble chat of a review bot's comment carries Geld's "Rerun" (sync glyph + word) on the byline's right, 8px from the slot's right edge as the words are from its top (the chat column is inset 16px, so the control hangs 8px past it), for bots with a trigger phrase; it posts the trigger like the request menu does and hides the bot's own re-trigger badge inside the comment (`AGENT_RERUN_CONTROLS`: Greptile's `app.greptile.com/api/retrigger` link; the mark `data-geld-agent-rerun` is read only by the chat's CSS, so the node is itself at home). Running — the bot's verdict, or a click within `RERUN_PENDING_MS` (`visit.rerunPending`), taken on in place at the click before the pass sees the comment — turns the border transparent (never removed: the box keeps its size), fades the control, spins the glyph, keeps the word (so nothing shifts), uses the default pointer and GitHub's own `tool-tip` element ("Greptile is running"; the page's custom element upgrades ours); a click then opens a Primer `Overlay` dialog ("Greptile is already running" · Cancel focused · "Rerun anyway") before posting a second trigger. **The same control stands on the pinned strip** over a thread's chat while the strip is open (`ChatSource.rerun`/`latestAnchor`, `sourceControl`, `.geld-review__chat-pin-row`), and the badge is hidden there too. **An older word of the bot's gets "See latest" instead** (`latestControl`, `ChatByline.latest`; the history glyph mirrored with `scaleX(-1)` — Octicons have no forward one — in Rerun's box, so the line never shifts): the strip showing how the summary read when the thread was opened (`revision`) leads to the comment's own row, and a comment from an earlier run where the bot has since posted a newer *summary* — `newerSummaryAnchor` in panel-model.ts, the bot's newest report-shaped comment in the crawl's `sourceFacts` (`botSummaryFor` with no cutoff; a status line, a trigger, a *refusal* — `refusalReason` — or a thread the verdict hangs on is not a summary, so a bot that refuses a re-run after an earlier review still leads to that review, not the refusal, and a bot that rewrites one comment in place has one anchor throughout) — leads to that one, through `onOpenAnchor`. Discovery (Oct 2026, six Mintlify PRs): Bugbot posts no root comment and no review body, edits only its thread comments and never links one comment to another, so nothing yet needs a two-comment view. Lines are ordered by how the bot is known (`BotPresence`): `seen` on the page (`/apps/<slug>` links in comments, the checks list and the reviewers box, payload verdicts and item sources, check runs by name, trigger comments), `declared` by the repository's `reviewBots`, `configured` by one of its own files in the repository (both from the controller's `repoBotsHint`, declared only once the config applies under the reader's `repoConfigs` choice), then `other`, the rest of the registry behind an "Other bots (N)" disclosure, since a trigger for a bot that is not installed is a public comment with a handle in it; with nothing pointing at any bot the registry is the list. Under a separator, Run ("Run Bugbot", "Run 2 bots", disabled with nothing ticked) posts one trigger comment per ticked bot in sequence (`postTopLevelComments` waits for GitHub's form to clear between posts) and Cancel, Escape or a click outside closes. `mountPanel` does not rebuild while the menu is open (the picks would be lost); closing it calls `onRequestMenuClosed` → `reapplySoon`, so whatever changed meanwhile renders then. The Review bots row therefore shows on every PR conversation, with "No reviews yet" until a verdict exists. An open item's notes link to each source bot's run summary (`bots[].sourceId`). Quick view takes the **outermost** node per comment id — GitHub puts `issuecomment-N` on the comment group and on the comment inside it, which used to yield two cards — and moved nodes drop `hidden="until-found"` while away (a folded event row otherwise rendered as nothing in the slot). "Copy digest" (`digestMarkdown`) carries the TL;DR, CI/review status, one line per bot with its traffic light, a link to its run summary and an excerpt of what it said, then every item — so it is useful on a PR with no review threads. The "add the Geld Action" pointer is a persistent, undismissable line *under* the box (`.geld-review-nudge`), shown only while the page has no summary comment. **The panel is rebuilt on every change, so focus is restored by key** (`data-geld-focus`, `preventScroll`): besides keyboard users, the focused element is Chrome's preferred scroll anchor, which is what kept the row under the pointer from drifting when late content (avatars, bot images) settled in the slot; the slot also sets `overflow-anchor: none`. Rows are an accordion: at most one is open (`visit.openKey`, `item:<id>` / `fold:<key>` / `checks`), and the open row's slot shows the **quick view** (`review/quick-view.ts`): the row's *whole timeline nodes* — a review thread's row with every comment, its reactions, each comment's own ⋯ menu, the collapsible "Reply…" box and Resolve — **moved** from the timeline (`review/teleport.ts`: a comment node holds each one's place, `data-geld-teleported`, `hidden="until-found"` lifted while away, `restoreAll()` before the panel is rebuilt or torn down) and compacted by CSS (rail, avatar gutter and file header hidden; headings capped). GitHub sees its own DOM, so replying, resolving, reacting, editing and quoting behave exactly as in the timeline. **React-owned nodes (the merge box, and the conversation timeline for accounts on the React PR page) move too, live, never cloned** — a clone has none of React's handlers, which is what made the CI list's gear and ⋯ menus dead. Two things a loaned React node needs can only be done in the page's own JavaScript world (the content script's isolated world shares the DOM but not JS objects, so own properties it sets on nodes are invisible to React), so `entrypoints/portal.content.ts` runs with `world: 'MAIN'` (manifest for github.com; `inject.ts`/`enterprise.ts` add it best-effort where `scripting` accepts `world`): (1) while a child is on loan its parent gets instance `insertBefore`/`removeChild`/`replaceChild` that treat the placeholder as the node, so React's next commit does not throw and blank an error boundary; (2) React listens on its root container and finds the handler from the event's target, and a node under our panel is outside that container, so the portal re-dispatches a copy with the same `target` on the node's home root (skipped when the root already contains the panel). The protocol is DOM-only: `data-geld-teleported="<token>"` on the node, `<!--geld:quick-view:<token>-->` in its place, `geld:portal-lend`/`geld:portal-return` events on the parent; nested loans (a header worn by a row, out of a comment that is itself on loan) inherit the root through the loan. Without the portal (no MAIN-world support) everything still works except React's own controls inside a quick view. Tokens also let a *second* Geld instance (a re-injected content script) send another instance's nodes home (`reclaimOrphans`) instead of removing GitHub's comments with the old panel, and `restoreAll` never removes a node whose placeholder is gone — someone else owns it now. **An open row wears its first comment's header** (`wearHeader`: everything before the body in the comment container — author, time, labels, reactions trigger, ⋯ — into the row's `head-slot`) and shows the body alone below; the crawler reads worn pieces through `wornPiecesOf` (transitive) so a comment keeps its author, time, avatar and — for a review — its comment while on loan. *Reviews* row: review verdicts (`crawlReviews`, `pullrequestreview-N`, state from the row's own sentence, never the comment's words) fold out of the timeline in compact mode and list under the row as an index of people's reviews and remarks (`renderCommentsList`: state glyph, avatar, name, one-line preview, thread count, time, a right chevron; each line goes to the round where it opens); the heading names every reviewer once by their latest verdict (`reviewerGroups`: ✓ approved, ✕ changes requested, comment, ● awaiting — glyph, avatars, "2 approved"; a later comment-only review does not withdraw a verdict, a re-request moves them to awaiting; people's top-level comments are not reviews and stay off it). **The heading reads the sidebar first** (`crawlSidebarReviewers`: the Reviewers block's `[data-assignee-name]` rows, each with the picture and a status control whose tooltip says the sentence — "X approved these changes", "X requested changes", "X left review comments", "Awaiting requested review from X", a dismissed review — the octicon's name as fallback; Apps are skipped, they are the Review bots row's): it is GitHub's own latest-per-reviewer and complete from the first paint, while the timeline's review rows sit at the end of a long conversation behind "Load more" and minimized groups and take seconds of fetching, during which the row used to say "No reviews yet" on an approved PR. `reviewerGroups(entries, sidebar)` takes the sidebar's word on a reviewer as final and the timeline's only for reviewers it does not list; the approvals count (`requiredReviewsFrom`) is seeded the same way; the open list shows a provisional line per sidebar verdict the timeline has not shown yet (`sidebar:<login>`, `isProvisional`: glyph, picture, name, nothing to open or go to) which the review's own line replaces as it lands. While the timeline is still being read — `timelineIngesting`: fragments in flight or still wanted (`deferredFragments`/`fragmentWanted`, shared with `loadMinimizedReviews`), or a "Load more" this visit will press; only with the compact timeline, which is what fetches everything — `PanelModel.ingesting` puts GitHub's in-progress ring (`ingestingMark`, `.geld-review__ingesting`) after the row's content (the Review bots row too while it has no chips), the empty states say "Reading reviews…", and the open list ends in "Reading the rest of the timeline…"; not a skeleton, since the verdicts shown are real. Preceded by `approvals/required approvals` only when the page states a requirement — the merge box says "At least N approving reviews" while unmet and "N approving reviews by…" (a count) once met, the sidebar's Reviewers block keeps saying "At least N approving review is required to merge" while the PR is open (`reviewersSidebarText`), and a merged or closed PR states it nowhere, so there the groups alone carry it (no "N approved" beside "✓ N approved"); the requirement seen is remembered per visit. Narrow (`@container` ≤ 640px): the fraction alone and the glyph-plus-avatars groups, no words. **Each conversation has one home**: the round (by type) or the push and its Needs attention row (by push). The Reviews row's list is an index (`renderCommentsList`, `entryRow(…, 'pointer')`, `[data-pointer]`, chevron right): one line per verdict, remark or pending request with a "N threads" count, and a click goes to the round through `onOpenAnchor` (`seatFor`, `revealRow`); threads are not listed there (`ReviewEntry.parent` still records a person's review for the crawl). **Times line up down a list**: every right-hand control is a 28px square (`.geld-review__chevron`, `.geld-review__ctl-slot--held`, `.geld-review__spacer`), and `entryRow`'s `reserveChevron` says a sibling line has the most squares a line in that list can have — in a round two (⋯ and chevron) when any line opens, in the Reviews index one (the pointer chevron) — so a line with fewer (a bare verdict: none; a verdict with threads: only its pointer chevron) leaves the missing squares blank. Per list, not per panel: a list where no line has a ⋯ lets every time sit against the edge. By push, an open thread listed inside its push is a pointer row to its Needs attention row (`itemRow(…, pointer)`, focus key `main:ptr:`); resolved threads open in the push. A verdict opens only when it wrote a comment (`entryOpens` = `hasBody`), as a one-bubble chat; a bare verdict is a static line with its thread count, since its threads are rows of their own in the same round, so no list of threads and no "No comments" callout is rendered anywhere. Narrow, non-sticky layouts (`stickyTopOf` returns null) keep GitHub's sizing and nothing is pinned. **Nothing in the sidebar is measured on the apply path.** `apply()` runs after every mutation batch, and while a large diff streams in that is many times a second with a layout GitHub has just dirtied; one `getBoundingClientRect`/`getClientRects`/`getComputedStyle` there forces a full layout (20–30 ms on a 124-file diff) on every pass — that was the extension's single biggest cost. So the apply path only writes attributes; every read (section boxes matched to GitHub's tree, the filter gap, pinned offsets, the overhang) happens in `SidebarGeometry`, a ResizeObserver callback (layout is clean there), reads-then-writes, and `refresh()` is called directly only for structural changes no size reflects (pinned set changed, a section removed). `SidebarSizer` takes the pane's rendered state and the viewport width from its observer entries instead of reading them, re-reads the sticky offset/direction only on real resizes, ignores scroll events that do not move the pane, and measures the overhang just after paint (`rAF` → `setTimeout 0`), because a streaming page scrolls itself via scroll anchoring with its layout dirty. The same rule holds elsewhere: the header label reads its neighbour's computed font once; `headerNodesAdded` only fires for a real "Lines changed:" span outside a diff entry (a streamed file is full of `sr-only` spans), the page-wide header scan is cached until a host leaves the document or such a span arrives, and the head SHA (a regex over GitHub's embedded JSON payload) is read once per page state. Profile with a CPU profile attributed to extension frames on `vitest/pull/10554/files` started right after `domcontentloaded` before touching any of this.

- **A loaned node must read the same as it does at home, or the panel loops.** The panel is swapped whenever its signature changes; a swap returns every loan and re-makes it; the next crawl reads the nodes where they now are. - **What a pass costs is bounded by what changed, and nothing runs in a hidden tab.** The controller's observer callback decides in this order: Geld's own elements → nothing; `document.hidden` → note it (`hiddenDirty`, the crawl cache is dropped) and return before any DOM read, with the first `visibilitychange` back running one full pass synchronously in the handler, before the tab's first paint (`schedule`, `apply`, the pre-paint header path and a settings change defer the same way; the review panel's own re-apply paths set a flag the catch-up takes, `takeReviewDeferred`; the tooltip and hovercard close on hide; the sidebar sizer leaves its frame to the browser, which holds rAF until the tab shows); a batch that is only clocks (`isClockTick`: text under `relative-time, time-ago, time`) → `refreshReviewTimes()` and nothing else; then **regions** (`src/github/regions.ts`): a batch entirely in the document head, the global navigation, the footer or a Primer tooltip (`chrome`, a third of all batches measured on github.com in Oct 2026) schedules nothing, and the rest is classified by the containers the adapters, crawler and list surfaces already know into `lists`, `conversation`, `files`, `header`, with `unknown`, a batch over 300 records, or a change of page state meaning the full pass. The debounced pass (`applyScoped` → `runPass(scope)`) skips the files adapters on a conversation-only batch, the review pass and the chips on a files-only batch, and runs the header every time; every caller other than the observer gets the whole page (`schedule()` without arguments, `apply()`). **Clocks**: current github.com ticks `relative-time` inside its shadow root, which no observer of the page sees, so the panel's time cells (`data-geld-time-for="<anchor>"`, `timeCell` in panel.ts, `timeAnchor` on chat bylines, `FoldRow.timeAnchor` on fold rows) are refreshed every 10 s while the tab is shown (`scheduleTimeRefresh`; the page's clocks each tick at their own second, and a fixed minute between reads left a cell a whole minute behind) and by a light-DOM tick; the loan watcher ignores clocks and the panel's own cell writes. **The crawl re-reads only what a batch touched**: `crawler.ts` keeps each comment's, thread container's and event row's reading in a `WeakMap`, `markCrawlDirty(records)` (called by the controller with every classified batch) marks the comment, thread and event above each record's target through loans (`closestAtHome`) and through GitHub's repeated ids (`markUp` walks every carrier), and `resetCrawlCache()` drops it all. **Resolving through GitHub's button in an opened chat**: the classic Resolve answers with the whole thread's resolved partial in a fresh `<turbo-frame>` — header, `data-resolved`, `data-hidden-comment-ids`, and the comments behind a lazy fragment again — swapped in for the loaned node inside the panel. The loan watcher (`watchLoans`) adopts the frame as the loan (`adoptReplacements` → `adoptReplacement`, the token moves) and that adoption *is* the state change: judged afterwards, `touchesThreadState` reads the token-bearing newcomer as the panel's own move and the detached old node has no `closest()`, so the record said nothing and the resolved thread sat open in its row until a rebuild for another reason sent the loan home (mint#12367). And since the swapped-in container holds no comment until its fragment is fetched once more, `readThread` answers for such a container from `rememberedThreads` — the last full reading, keyed by the deferred URL and by every `discussion_r<id>` it held or names — with the new container's `data-resolved`, re-reading it every pass (`dirty.add`) until the comments land; without that the thread left the digest for a second and came back resolved. **Idle work** (`lib/idle.ts`, `whenIdle(key, fn)`, keyed so a newer pass replaces a request still waiting, 500 ms ceiling): Jev's batch submission, the diffstat surfaces and re-arming the commit-link tooltip. **Storage**: `DiffCache` gathers entries for 250 ms and stores them in one read-merge-write, the worker writes its throttle state once per burst, and a tab hidden when another tab's cache write arrives keeps the latest version and rebuilds its map on the first read after it shows. **Measure before guessing**: `lib/perf.ts` times named phases (`phase`, `phaseSince`, `count`) as `performance.measure`s (DevTools Timings track) and a per-tab table; the options page's Copy diagnostics asks every GitHub tab for its snapshot (`geld:perf-report`, `lib/perf-report.ts`) and appends one block per tab, nothing written or sent. **Each block ends with the script's lifecycle trail** (`mark()` in `lib/perf.ts`, `PerfSnapshot.trail`: `script-start → settings → catalog → controller-start → published`, plus `redirect-early`, `sign-in-page`, `retired:takeover` / `retired:invalidated`), so a tab where Geld showed nothing says where its script stopped; a *retired* copy still answers the perf report, late (`RETIRED_ANSWER_MS`), so its trail is what gets reported when no live copy is there, and a copy that retires before its controller ran also says so in the console (`[geld] stepped aside before starting…`); a tab that answers nothing at all is listed as such. The background's injection decisions (`ensureContentScript`, `lib/inject.ts`) land in the same session log as `inject <tab> injected|present|failed on=install|activated|popup`, since a second copy taking a page over is how the two-copies flicker began. **"Report with diagnostics"** (`report-diagnostics`, extension-only, beside Copy diagnostics) opens a new GitHub issue from the `diagnostics.yml` form with the same report, version and browser filled in and an optional "What was happening?" field; it links **straight to GitHub's `issues/new?template=diagnostics.yml`**, not through the site like Feedback does: the report names pull requests (private ones included) and rides in the query, so the only host that sees it is the one the issue goes to, and only when the form is opened — the privacy page's "nothing about your browsing is sent anywhere" holds. Nothing is posted until the issue is submitted, and no sign-in with Geld is needed: GitHub asks for its own if the reader is signed out there. Templates are read from the default branch, so the form is live once this is on `main`. `local:debugScopes` (set from the harness, never the UI) runs the full pass after every scoped one and logs `[geld] scope disagreement`. - Line counts come from the page when it renders per-file diffs; otherwise (PR conversation tab, PR lists, partially loaded large PRs) the background fetches the same `.diff` GitHub serves, via `entrypoints/background.ts` (needed because github.com redirects to `patch-diff.githubusercontent.com` without CORS). Parsed diffs are cached in `storage.local` as `github:{owner}:{repo}:{pull}:{sha}` (`…:commit:{sha}` for commits; `github@{host}:` on Enterprise); writing a new SHA for the same pull drops the old one. **Header counts on PR/commit pages come only from that diff, never from the DOM**, so they change at most once (GitHub's number → ours); DOM totals are used only where no commit key exists (compare pages). The head SHA is read once per page from GitHub's embedded payload (`detectHeadSha`) and cached; the React files view reloads its data in place on the "new changes" refresh without touching that payload, so `watchFilesRefresh` (a `PerformanceObserver` on resource timing, which sees the page's own `changes?_json=1` fetch from the isolated world) asks GitHub's Commits-tab JSON for the newest commit (`fetchHeadSha`) and re-keys the diff when it changed. The content script runs at `document_start` and rewrites the header synchronously inside the MutationObserver callback (before paint) whenever a settled or cached value exists, because GitHub's React header re-mounts several times while a page streams in. **Rate limiting is the failure mode to design against**: GitHub's `.diff` endpoint serves roughly 45–48 requests in a burst and then answers 429 to *everything* for a minute or more (no Retry-After), so two unpaced list pages used to blank every row and every PR page opened during the block. The background therefore paces diff fetches through a persisted sliding-window budget (`DIFF_BUDGET` per `DIFF_WINDOW_MS`, `local:diffThrottle`; requests wait for a slot rather than fail), and a 429/403 starts a cooldown that doubles per consecutive strike (60 s → 15 min cap, or Retry-After when given) and is reported to the content script as `retryAfterMs`, which schedules the row's retry just after it. **The page's own subject comes first**: a request carries `priority` (`page` = the header of the pull request or commit being read, a commit the reader hovers; `background` = list rows and refreshes of stale counts), `PAGE_RESERVE` slots of the budget are only for `page` requests, and a `page` request goes to the front of the content script's queue, so opening a pull request after browsing a list never waits out the window behind rows. **The diff host also answers 503 in waves** (GitHub's "Unicorn!" page from `patch-diff.githubusercontent.com`, measured: seven of eight concurrent requests one minute, ten of ten fine the next). That is a busy pause for the rows (`BUSY_COOLDOWN_MS`, growing only when the next wave follows the pause; every answer within a wave is the same pause, not a longer one; any success ends it), never a strike, and the page's own subject is not held by it: it probes through and asks again on `PAGE_BUSY_RETRY_MS` (1.5 s, 3 s, 6 s, 12 s). A page github.com serves in a diff's place (its sign-in wall, an organisation's SSO prompt "Sign in to Mintlify", an interstitial) reads as `signed-out` by its title and **gives its budget slot back** (`refundTurn`): it never reached the diff host, and charging it meant a lapsed SSO session cost a page of rows the whole budget, so every row waited out the window after signing in again. The options page's "Copy diagnostics" log records each fetch's outcome, status and answering host. **The page's own pull request has a second source for its header:** the diff host answers 503 for a minute or more to a pull request whose `.diff` nobody has asked for yet (a freshly opened one, measured: nine 503s over 75 s for a single request), so the moment a `page` request comes back anything but ok, `DiffSource` fetches GitHub's own files-tab data (`/owner/repo/pull/N/changes?_json=1`, same origin, session cookie, `payload.…diffSummaries[]` with `path`/`changeType`/`linesAdded`/`linesDeleted`; `@geld/core/diff-summaries.ts`) and reports it as a `provisional` ready state; the diff keeps retrying and replaces it when it lands (same numbers, plus binary/whitespace/comment facts), and nothing provisional reaches the disk cache (one exception: a diff the worker calls too large never lands, so its summaries are kept under the head's key). The summaries URL is the pull request's, not the head's, so they are asked **once per head** (`summariesHead`, per diff URL: the SHA asked for, or null before the page knew it — a later request for the same head with the SHA re-uses that answer; a request under a *new* SHA, the files view's "new changes" refresh re-keying the diff without a reload, drops the old head's `provisional` and `tooLarge` entries and asks again, and an answer to an earlier ask (`summariesAsk` generation) is discarded so an old head's counts never show as the new one's; `diff-source.test.ts`). The worker is stopped after ~30 s idle, so its in-memory diff cache is short-lived; the content script's disk cache (`DiffCache`) is what avoids refetching: SHA-keyed entries for pages (`github:{owner}:{repo}:{pull}:{sha}`, exact and never stale), plus `…:{pull}:latest` entries for list rows — the list markup carries no head SHA (verified: none in the page), so these are served stale-while-revalidate: shown for up to 24 h so a row is never blank, refreshed through the budget once older than 30 min, and a SHA-keyed write (opening the PR) refreshes `latest` too. A failed revalidation keeps the stale counts on screen. Four concurrent fetches per tab, only for rows near the viewport. **No GitHub API is used.**
- Browsers do not inject content scripts into tabs that were open before an install/update. `src/lib/inject.ts` puts Geld there on demand: the background injects into every open GitHub tab on `onInstalled`, into a GitHub tab on `tabs.onActivated` when it does not answer a ping, and when the popup gets no answer (`geld:ensure-content`, then one retry). The content script dispatches a `geld:takeover` event on start so an older copy still running in the page retires (and `ctx.onInvalidated` retires orphans), so there is never more than one active instance. **A retired copy must be inert and must keep answering the ping.** Inert: `controller.stop()` → `teardownReviewOverview()` nulls `lastSettings` (the overview's "mounted" sign), drops the pending `reapplySoon`/`fragmentLanded` timers and aborts the fragment fetches in flight (`fragmentAbort`); every asynchronous re-apply (`reapplyNow`, `reapplySoon`, `fragmentLanded`, the AI run's `reapply`) checks `lastSettings` first. - **The pattern catalog updates without a store release.** The built-in categories, their groups and globs are authored once, in TypeScript (`@geld/core/categories.ts` + `test-patterns.ts`), wrapped as `BUNDLED_CATALOG` (`Catalog` = `{ version, minExtensionVersion, categories }`). `pnpm catalog:build` generates `catalog/patterns.json` from it and `pnpm catalog:sign` writes `catalog/patterns.sig` (Ed25519 over the file's exact bytes, private key in the `GELD_CATALOG_PRIVATE_KEY` env var, held by the owner outside the repo; `pnpm catalog:keygen` prints a new pair, the public half lives in `catalog-key.ts`). CI runs `pnpm catalog:check`, which fails when the JSON drifted from the TypeScript or the signature no longer matches. A pull request from this repository that changes patterns would always fail that check (its committed `.sig` is stale and only the push to `main` can commit a new one), so the PR run first regenerates and signs the catalog in the workspace with the same secret, committing nothing; a fork's PR gets no secrets and still shows the stale signature. **The key never shares a runner with pull request code:** two jobs precede `check-and-pack` on a same-repo PR — `catalog-build` (the branch's checkout, no secret) runs `catalog:build --auto-version` and uploads `patterns.json`, the bumped `categories.ts` and `catalog-key.ts` as an artifact; `catalog-sign` checks out the *default branch*, downloads that artifact and runs `node scripts/catalog-sign.mjs` with `GELD_CATALOG_PRIVATE_KEY` (nothing from the branch executes there: no install, no pnpm, the artifact is data the signer reads), uploading `patterns.sig`; `check-and-pack` downloads both over its tree before `pnpm check`. Splitting *steps* was not enough — anything a branch runs earlier in the same job (pnpm scripts, a `node` on `$GITHUB_PATH`, a process left behind) can reach a secret a later step holds. **Publishing a catalog change:** edit the TS → bump `CATALOG_VERSION` (`YYYYMMDD`, or +1 for a second release that day; the build refuses a content change without a higher version) → `pnpm catalog:build` → `GELD_CATALOG_PRIVATE_KEY=… pnpm catalog:sign` → commit all three. Installed extensions pick it up within a day; **the site renders from the bundled TS, so it needs a deploy** (core changes trigger one on Vercel). **Ids are permanent:** settings and gists refer to `category` and `category/group` ids, so the build fails if an id from the previous committed `patterns.json` is missing — deprecate a group by emptying its `patterns`, never by deleting it; adding a *category* still needs an extension release (it needs a default, and `resolveCatalog` ignores categories the build does not know). **Trust model** (`@geld/core/catalog.ts`): the extension (`src/lib/catalog.ts`) fetches the two files from `api.github.com` (contents API, raw media type — already a host permission; `raw.githubusercontent.com` would need a new one and disable the extension in Chrome until re-approved) on install, on browser start (at most every 6 h) and via a daily `alarms` alarm, verifies the signature *before* parsing, validates the whole document (`parseCatalog`: shape, `[a-z][a-z0-9-]*` ids, known icons, every glob compiles), and stores it in `storage.local` (`local:catalog` = `{ version, fetchedAt, json }`) only if `minExtensionVersion` ≤ the manifest version (first three numeric parts) and `version` is higher than the active one. `resolveCatalog(bundled, fetched)` takes content (groups, globs, titles, descriptions, icons, nouns) from the fetched file and policy from the bundled one — `defaultEnabled` and the set of categories can only change in code, so a remote file can never turn a category on for everyone; groups are unioned so nothing a setting refers to disappears. A 403/429 backs off until GitHub's `x-ratelimit-reset` and is not shown as an error; every other outcome lands in `local:catalogStatus`, which the options page's "What to hide" card shows ("Built-in patterns (v…)" / "Patterns updated … (catalog …)", "Check now", last failure reason). `autoUpdatePatterns` (General, extension only) opts out; "Check now" still works. Everything that lists or matches built-in categories takes the catalog as an argument (`createMatcher`, `allCategories`, `categoryById`, `describeAdvancedSettings`, `validateSettingsDocument`, `readRemoteValidated`…), defaulting to `BUNDLED_CATALOG`; the content script, popup and options page `loadCatalog()` on start and `watchCatalog()` for changes. The pure parts (parse, verify, resolve, version compare) are in core and unit tested; only the fetch/cache/alarm wiring is in the extension.

The tooltip is `position: fixed; z-index: 1001`, one above the hovercard's inline `z-index: 1000` (both are `<body>` children, so only z-index decides); fixed rather than absolute because hosts sit inside sticky headers, scrolling panes and overlays, and a viewport-positioned box escapes all of their clipping and stacking with one routine. **The PR header's own counts get a flush box** (`attachBreakdownTooltip(…, { align: 'end', flush: true })`, header-stats.ts): the header's counts sit right above the tab bar's bottom border, so `position()` looks for that bar (`barUnder`: an element with a bottom border within 24px under the host, spanning it, among the host's ancestors and their children and grandchildren, since GitHub's tab nav is in a flex wrapper beside the counts' wrapper), lays the box's top border exactly over the bar's (`top = bar.bottom − bar's border width`, unrounded, as is `left`, because the host's right edge is fractional at most zoom levels and a rounded box ended half a pixel short), and sets `data-flush` so the top corners are square: the box hangs from the bar as a drawer. Geometric, not class-based, and re-checked on every reposition, so a narrow layout that moves the counts off the bar gets the floating box; the narrow mirror and every list chip never ask for it. Both end alignment and the flush box hold only when the underlined count sits at the host's end (`END_SLACK`, 160px, which the PR header's "+N −M" and blocks fit within): the classic compare and commit headers make the whole "Showing 29 changed files with 5 hidden, …" line the host, and aligning to its right edge put the box at the far side of the page with the caret left on the count, so there the box is centred on the count as elsewhere. Chip spacing: `--geld-chip-gap` (`.geld-pr-stat`, github.content/style.css) is the gap on *both* sides of the "•" — text→bullet is the chip's margin, bullet→counts the first count's — so a surface widens it by setting the one variable, never `margin-left`. When GitHub changes markup: edit the spec, push; CI publishes the catalog, extensions pick it up within six hours — no store release. New behaviour (placement modes, source kinds) is code.
- **Diffstats for other commits/PRs (hovercards) are catalog surfaces too** (`DiffstatSurfaceSpec` in `@geld/core/list-surfaces.ts`, `catalog.diffstatSurfaces`, applied by `src/github/diffstat-surfaces.ts`). A spec names the container (`root`), where the subject is written (a root attribute or a link's href containing `/owner/repo/commit/<sha>` or `/pull/<n>`), the diffstat `host` and its `additions`/`deletions`/`srOnly` elements, plus optional `css`. The extension requests the subject's `.diff` through `DiffSource` (cached per SHA), classifies it with the repo's matcher and rewrites with `applyHeaderStats` via `statGroupFrom`, so the label, tooltip and sr-only sentence match the page header. Idempotent per host via `data-geld-diffstat="<diffUrl>|<totals>"`. Bundled: `commit-hovercard`.
- **"Hide whitespace changes" (`hideWhitespace`) is URL state on GitHub, and Geld treats it as such** (`src/github/whitespace-viewed.ts`). `?w=1` on a diff page hides them, `?w=0` is what GitHub's diff-settings menu writes when the reader unchecks the option, and the React files view persists nothing between pull requests (verified Oct 2026: the menu toggle only rewrites the URL, and the next PR loads with `viewSettings.hideWhitespace: false` again). The former design assumed GitHub remembered the choice and set a `local:whitespacePersisted` flag after driving the menu once, after which it never re-applied; that flag is gone and the menu is no longer driven. Now the content script redirects at `document_start` (`redirectEarly`, before the settings-independent work and before GitHub renders anything) when a `pull-files`/`commit`/`compare` page has no `w`, the setting is on and the page is not opted out; `WhitespaceRedirector.ensure` does the same for SPA navigations once the view exists and submits the legacy view's own `/diffview` form instead when it is there (GitHub persists that one). **Opt-outs are per page key** (`/owner/repo/pull/N`, a commit's or compare's path) in `local:whitespaceOptOuts` (key → when, oldest dropped past 300): a `?w=0` records one, a `?w=1` on an opted-out page clears it (only the reader can produce that, since Geld neither redirects nor rewrites links for opted-out pages). `rewriteFilesLinksForWhitespace` adds `?w=1` to the Files tab and its per-commit forms (`/files/<sha>`, `/changes/<base>..<head>`) for pages not opted out. A redirect GitHub strips the parameter from (the document that follows within 4 s has no `w`) marks the path `unsupported:<time>` in `sessionStorage` for a minute, not the session, so a stray hit on that guard costs little.
- **Narrow screens keep the header counts.** GitHub hides the PR header diffstat by container width (its wrapper is `PullRequestHeader-module__hideWhenVeryNarrowContainer`). `syncNarrowMirror` (header-stats.ts) keeps a copy, `.geld-header-mirror` (label + `+N −M`, same tooltip provider), appended to the state-label row (`[data-component="StateLabel"]`'s parent in the same `[data-component="PageHeader"]`, so after the stack button) and toggles its `hidden` on every apply from whether the original host has client rects; the controller re-applies on `resize`. Removed with `restoreHeaderStats`.
- **The tooltip closes when its host leaves the DOM.** GitHub's React lists re-render rows wholesale (the merge box's stack list when the PR's state changes), removing a hovered chip with no `mouseleave`; the fixed tooltip then sat at stale coordinates or snapped to the viewport corner once `follow` measured an empty rect. While a tooltip is shown, `ui/tooltip.ts` observes the document (childList + `hidden`/`style`/`class`) and, one frame after a burst, hides the tooltip if the host is disconnected or has no client rects (`hostGone`); `position()` checks the same before measuring. The re-added chip gets its own tooltip on the next hover.
- **Diff fetch pacing and diagnostics.** The worker's `fetchDiff` never sleeps inside a message: when the 30/min budget is spent it answers `{ reason: 'queued', retryAfterMs }` and `DiffSource` keeps the row `loading` and re-asks then (with jitter) — a worker sleeping in a timer is idle to Chrome, which stops it after ~30 s and closes every pending port ("message port closed", normalised to `port-closed`). Transient failures retry on `TRANSIENT_RETRY_MS` then keep going at its last step up to `TRANSIENT_MAX_ATTEMPTS`. The diff endpoint also answers **503** (sometimes 502/504) to a burst — measured headless: a third of a page within seconds, well under the budget — which is GitHub busy, not a block: `recordBusy` pauses everyone 12 s, doubling to 60 s while they keep coming (`cooldownReason: 'busy'`, separate from 429/403 strikes, reset on success), and the page treats `busy` like `queued` for up to `BUSY_MAX_WAITS` pauses before the row says "GitHub busy". Measured after this: three list pages (75 rows) opened at once all count within ~2.5 min with no failed chip; the budget, not failures, sets the pace. `DiffCache` writes merge into the *stored* map (read-merge-write, serialised per tab) and every tab follows the stored map via `watch`; writing a tab's own snapshot used to drop the entries other tabs had added. `src/lib/diagnostics.ts` keeps a ring of ~300 events in `session:diagnostics` (worker starts, per-fetch outcome/timing/budget by `owner/repo#N`, rate-limit strikes, cache clears — no URLs, bodies or tokens); the options page's "Copy diagnostics" (`copy-diagnostics`, extension-only) puts them on the clipboard.
- **A diff that could not be had is never cached, and the row says so.** Signed out of a private repository, GitHub answers a `.diff` request with 404 (`text/plain` "Not Found"); with a lapsed SSO session it answers 200 with its sign-in page, which parsed as a diff of no files and used to be cached and shown as `0 hidden +0 −0`. `fetchDiff` (background) now fails with `signed-out` when the response was redirected to `/login`, `/session*`, `/sso` or `/orgs/*/sso`, and with `not-a-diff` when the body is HTML (`looksLikeHtml`); neither is cached, and nor is `http-404` any more (a 404 is the signed-out answer too). `DiffSource` treats those as definitive for the page — no retries spending the rate budget; signing in and reloading is the fix — and refreshes any on-disk entry that has zero files (poisoned entries from older builds). `pr-list.ts` `renderFailure` puts the reason in the chip's place (`.geld-pr-stat__failure`, muted italic: "sign in to count", "counts unavailable", "counts paused", "diff too large"; the `title` explains). The options page's "Clear cached diffs" also empties the worker's ten-minute memory cache (`geld:clear-diff-cache`). The action is extension-only (`surfaces: ['extension']`): the site has no channel to the extension's `storage.local`.
- **Commit links get the breakdown tooltip on hover intent** (`src/github/commit-hover.ts`, gated with the list chips by `showListStats`). Any same-origin link to `/owner/repo/commit/<sha>` or `/pull/N/{commits,changes,files}/<sha>` (the PR timeline, the Commits tab — whose React version links each commit to `/changes/<sha>` — and branch commit lists) counts, except links GitHub already gives a commit hovercard (`data-hovercard-url` containing `/commit/`, rewritten by the surface above) and the page's own URL. A PR can list hundreds of commits, so nothing is fetched up front and no link gets a listener: one delegated `mouseover`/`mouseout`/`focusin`/`focusout` on the document, and a link must rest under the pointer for `HOVER_INTENT_MS` (300 ms; focus is immediate) before `DiffSource.request` runs for `/commit/<sha>.diff` (cached per SHA). Until the diff lands the tooltip shows skeleton rows in the breakdown's shape (`showTooltipLoading(host, LoadingShape)`: "Essential" + one hidden row + "Total" when any category is on — a commit rarely touches more than one — else a single row; known labels as text, Primer-style shimmering bars for the numbers, still under reduced motion; "Counting" for screen readers only); the diff source's `onChange` re-applies, and `applyCommitHover` re-presents the armed link when its state object changed. Rate-limit and definitive failures get a one-line message. Subject parsing shared with the diffstat surfaces lives in `src/github/subject.ts`.
- **Chips never repeat the page's own PR in the merge box checks list**: each check row's name links to `/pull/N/checks?check_run_id=…`, which `findRows` (`pr-list.ts`) skips by the query parameter, so the `react-list` surface (which those `li[role="listitem"]` rows otherwise match) leaves them alone. The stack list *does* include the current PR on purpose — every stack entry gets counts.
- **Pull requests hidden by author** (`@geld/core/pr-authors.ts`, `src/github/pr-authors.ts`, setting `hiddenAuthors`, section `lists`). Login patterns with `*` wildcards, case-insensitive, brackets literal (`*[bot]` = every GitHub App). the row's surface reads the author (classic: the "pull requests opened by X" link title; React list: `a[data-testid="author-filter-link"]`'s "Filter by author X" label; `author:app/<name>` hrefs → `<name>[bot]`); matching rows get `data-geld-author="hidden"` and each list gets one note (`.geld-author-note`, a `li` wrapper inside `ul` lists) with a Show that flips the list to `data-geld-authors-shown` for the visit. Stack-popover items carry no author and are skipped.
- **Repositories can configure Geld for everyone reviewing them** (`@geld/core/repo-config.ts`, `src/github/repo-config-source.ts`). A committed `.github/geld.yml` (and an org's defaults in `owner/.github`, `geld.yml` at the root or under `.github/`) uses the settings vocabulary — `categories`, `groups`, `categoryPatterns`, `customCategories` — and is checked by the same strict validator plus `collectRepoConfigIssues` (personal keys such as `enabled`/`repoRules` are rejected, unknown keys ignored). `.gitattributes` `linguist-generated` lines feed the Generated category via `generatedConfigFrom`. **A sign-in page at a repository URL gets nothing** (`isSignInInterstitial`, `page.ts`: GitHub marks its login, organisation SSO and 2FA pages with `session-authentication` on `<body>`; `runPass` and the pre-paint header path stand down there, since every request for the repository's data would answer 401 in the console). **No lookup may 404 in the page** — the browser prints every failed `fetch` as a red console error attributed to Geld, and most repositories have none of these files. So (`RepoConfigSource.readFile`): the repository's own files are fetched `/{owner}/{repo}/raw/HEAD/{path}` from the page origin (session cookie → private repos work; the redirect to raw.githubusercontent.com is CORS-open) but only after GitHub's directory listing (`/{owner}/{repo}/tree/HEAD[/dir]?noancestors=1` with `Accept: application/json` → `payload.tree.items[].path`, 200 whenever the repo is visible; memoised per directory) says they exist — an unusable listing falls back to the direct fetch. The org's `.github` repository is read by the background (`geld:fetch-file`) from `raw.githubusercontent.com/{org}/.github/HEAD/{path}` **without credentials**: the worker has no host permission there, CORS applies, and the host's `*` is only accepted uncredentialed (which is also why the worker cannot follow github.com's `/raw/` redirect; adding the host permission would disable the extension on update until users re-approve). That requires the `.github` repo to be public — GitHub's own rule for default community files. Enterprise hosts serve raw files on their own origin and are fetched by the worker with credentials. Text is cached per `github:{owner}:{repo}:{path}` in `local:repoConfigCache` for 30 min, and `GeldController.effectiveSettings(repo)` layers the valid configs (org, repo, gitattributes; later wins, user `!` rescues stay first) under `createMatcher`. The header waits for a pending lookup so it settles once. Gate: setting `repoConfigs` (`always` / `ask` / `never`, a `choice` schema field); `ask` answers are per repo in `local:repoConfigChoices` and taken in the popup, which also names whose config is in use and lists problems. Files hidden by a repo config are counted and listed like any other — that is deliberate, hiding is the attack surface. **One key is the repository's own: `reviewBots`**, a list of review-bot registry ids (`bugbot`, `coderabbit`, …) naming the bots installed on it, allow-listed rather than free logins because the extension knows what to post, read and show only for registry entries; core cannot import `@geld/review`, so `parseRepoConfig(text, catalog, knownBots)` takes the ids from the caller (`RepoConfigSource` passes `REVIEW_BOTS`; the site passes nothing and checks shape only), and an unknown id fails the file like any other problem, with the known ids in the message. The same directory listings answer which bots have one of their own config files in the repository (`ReviewBot.configFiles`: `.coderabbit.yaml`, `.cursor/BUGBOT.md`, `greptile.json`, `.github/copilot-instructions.md`, `.gemini/`, `.capy/`, `.codex/`; never `AGENTS.md`, which every agent reads) — `RepoConfigSource.botConfigs(origin, repo)`, memoised for the same half hour, independent of the `repoConfigs` setting since it reads the repository and applies nothing. Every key and valid value is documented on geld.sh/repo-config (`apps/site/app/repo-config/page.tsx`, rendered from `@geld/core` and `@geld/review/bots`, so the site depends on the review package too).
- **Popup and options styling mirrors the site**, not GitHub: `src/ui/base.css` declares the same oklch tokens as `apps/site/app/globals.css` with `light-dark()`, bundles Geist/Geist Mono variable fonts (`src/ui/fonts/`, OFL), keeps everything square except buttons and the account control (`corner-shape: bevel square` on TL/BR; where the property is missing — Safari — the `hyperellipse` polyfill is dynamically imported by `src/ui/corner-shape.ts` from the popup/options entrypoints only, reads the `--corner-shape` twin declared next to the native property, and `--corner-scale: 0` keeps corners square until it runs; the site does the same in `components/corner-shape-polyfill.tsx`, gated on `CSS.supports`, so Chrome never downloads the chunk), and uses the site's 36×20 switch with a 12px thumb. Change a token in both places or not at all.
- **Safari ships through a thin Xcode wrapper** in `apps/extension/safari/` (generated once with `pnpm --filter @geld/extension safari:project`, i.e. `xcrun safari-web-extension-converter --copy-resources`; committed, including the copied extension build under the extension target's `Resources`). Before every App Store archive run `pnpm --filter @geld/extension safari:sync`: it rebuilds the Safari flavour, rsyncs it over `Resources`, sets `MARKETING_VERSION` from `package.json` and bumps `CURRENT_PROJECT_VERSION`. Archive/upload happens in Xcode (`safari:open`, Product → Archive, Distribute App → App Store Connect); submissions must come from a release Xcode, not a beta. Bundle ids `sh.geld.safari` / `sh.geld.safari.Extension`.
- Toolbar icon dark mode: Chrome/Edge use an offscreen `MATCH_MEDIA` document; Firefox uses `theme_icons`; Safari tints template icons. Icons are pixel-snapped renders of `assets/brand/geld-logomark.svg` (see git history for the generator approach; regenerate at 1/2/3 px per grid unit).

## Website (apps/site)

A small, fast marketing site for geld.sh, not a docs site. Run it with `pnpm --filter @geld/site dev` (or `pnpm dev:site`); `pnpm --filter @geld/site check` runs typecheck, lint, unit tests and a production build, and is part of root `pnpm check`.

- **Stack:** Next.js 16 App Router with `cacheComponents: true`, Tailwind CSS 4, shadcn components generated on **Base UI** (`components/ui/`), the `cn` package for class merging, Geist via the `geist` package, `lucide-react` icons. Everything is prerendered; the only cached-async piece is the latest-release lookup (`lib/release.ts`, `use cache`, revalidated hourly, falls back to the Releases page when there is no release yet). Light/dark follows `prefers-color-scheme` by default; the footer's theme menu (`components/theme-menu.tsx`, `lib/theme.ts`) can pin a scheme via `data-theme` on `<html>`, persisted in localStorage and applied by an inline script before paint. Colour tokens use `light-dark()` keyed on `color-scheme`, and the `dark:` variant covers both cases (globals.css). Nothing on the site is rounded except the GitHub-imitating demo visuals (kept round on purpose). Calls to action — buttons, button-like links, clickable pills — use the `geld-corners` utility: square with the top-left and bottom-right corners cut via `corner-shape: bevel square` (size from `--geld-cut`, `geld-cut-*`), echoing the logomark; hover deepens the cut by 3px (a child inside `group/geld`, like the account avatar, follows its parent's hover), and an `::after` pseudo-element makes the hit area the full square plus 1px so the cut-away corners are still clickable. Browsers without `corner-shape` get plain square corners. Form fields, chips, cards, popups and badges are plain squares. Hover details that phones must reach (the count breakdowns) use `components/ui/popover.tsx` (opens on hover and tap), not the tooltip. The white brand SVGs are shown in dark mode by toggling two `<img>`s with that variant (`components/logo.tsx` references `assets/brand/` via `new URL(..., import.meta.url)`); the SVG favicon can only follow the OS.
- **Feedback goes through the site.** The extension's Feedback links (popup footer, options footer, `src/ui/feedback-link.ts`) point at `https://www.geld.sh/feedback?version=…&browser=…&page=…` (never a URL or a login), and `app/feedback/route.ts` forwards to a new issue on the repository with the issue form `.github/ISSUE_TEMPLATE/feedback.yml` pre-filled. The hop exists so the destination can change (a form on the site opening issues through the Geld App on a private tracker, once the source is closed) without a store release.
- **Pages:** `/` (hero, before/after PR header + hidden row built from `components/demo/sample-pr.ts`, which classifies its sample files with `createMatcher(DEFAULT_SETTINGS)` so the picture cannot lie; install buttons; live "try a path" demo in `components/path-tester.tsx`), `/how-it-works`, `/patterns` (rendered from `CATEGORIES` — the same source `catalog/patterns.json` is generated from — never hand-written; no runtime fetch, so a catalog change reaches the site with the next deploy), `/faq`, `/privacy` (doubles as the store privacy policy). Favicons are drawn from the brand SVGs at build time (`lib/brand.ts`); the OG image (`app/opengraph-image.tsx`) combines the wordmark with a real 2× screenshot from `assets/screenshots/` (embedded as a data URL, `loadScreenshot`). Re-capture that screenshot with the extension on a public PR when the header UI changes; the Vercel ignore script watches the folder.
- **Data that must stay in sync with the extension:** the version comes from `apps/extension/package.json` (`lib/version.ts`); patterns and categories from `@geld/core`; install links from the latest GitHub Release until store listings exist — set a URL in `STORE_URLS` (`lib/downloads.ts`) to switch a browser over. Author profile URLs live in `lib/site.ts` (entries with `url: null` are not rendered).
- **Deployment:** Vercel, dreamthinkbuild account, Root Directory `apps/site`, domain geld.sh. `apps/site/vercel.json` points the Ignored Build Step at `scripts/vercel-ignore.sh`, which skips builds for commits that only touch the extension (core, the extension's `package.json`, brand assets and the lockfile do trigger builds).
- **No database, ever.** The only user data is the settings gist on the user's own GitHub account. The site signs users in with the **same Geld GitHub App** as the extension, via the web flow (the App's callback URLs are `https://www.geld.sh/auth` and `http://localhost:3000/auth`; the extension's device flow never uses them). The canonical host is **www.geld.sh** (`SITE_URL`); the apex 308-redirects to it. `callbackOrigin()` returns the same origin as `authOrigin()` and must match a registered callback exactly. Code: `app/auth/start` (state cookie + redirect to GitHub; no `scope`, the App's permissions decide), `app/auth` (callback: verify state, `exchangeCode` from `@geld/github`, `fetchGitHubProfile`, set cookie; if the previous session was an OAuth App one, revoke that token with the legacy credentials), `app/auth/signout` (POST: clear + best-effort revoke with whichever app issued the token), `app/auth/refresh` (renews an expiring App token and redirects back; pages redirect here on `stale`), `app/auth/expired` (pages redirect here on `SignedOutError`). Only routes/actions may write cookies, so **`resolveSession(config, writable)`** in `lib/auth/session.ts` is the one entry point: with a cookie store it refreshes inline (server actions, route handlers), with `null` it only peeks and returns `stale` for a token within five minutes of expiry (pages). `lib/auth/config.ts` reads `GELD_APP_CLIENT_ID`, `GELD_APP_CLIENT_SECRET`, `AUTH_SECRET` (all server-only; `AUTH_SECRET` derives the AES-GCM key in `lib/auth/crypto.ts`) plus the optional legacy `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` used only to revoke OAuth App tokens, and the redirect origin comes from `authOrigin()` — `http://localhost:3000` in development, `SITE_URL` otherwise, never from request headers. The token pair (access + rotating refresh token, `lib/auth/session-model.ts`) lives only in the encrypted HttpOnly `geld_session` cookie (30 days, rewritten on every refresh); a readable `geld_account` cookie carries login + avatar for the header. Old cookies without the new fields read as `auth: 'oauth'` sessions and `/settings` shows the shared `ReconnectNotice` above the form. `/settings` renders `sectionsFor('site')` and reads/writes the gist with `@geld/core/gist-sync` through server actions (`app/settings/actions.ts`) that re-read the gist (strictly, via `readRemoteValidated`) before layering a change on it; an `invalid` gist renders the shared `CORRUPTED_SETTINGS_COPY` alert (`components/settings/corrupted-settings.tsx`) with the issue list, an Open gist link and a reset-to-defaults action instead of the form, and saves are refused until it is fixed. The site accepts no uploaded files today; if it ever does, run them through `validateSettingsDocument`. `/auth*` and `/settings` are dynamic; everything else stays prerendered.
- **Auth environments.** Production has the App variables (and, during the migration period, the legacy OAuth ones) in Vercel. **Preview deployments deliberately have none** (their hostnames are random, so no callback could be registered) and `authConfig()` additionally returns `null` whenever `VERCEL_ENV` is not `production`, so `/settings` shows "Sign-in isn't configured in this environment" and the build still succeeds. Local development uses the *same* App (its `http://localhost:3000/auth` callback); put the values in `apps/site/.env.local` (see `.env.example`, or `vercel env pull` from the Development scope) with a different `AUTH_SECRET` per environment. Without real credentials the flow can be exercised against a fetch mock, which is how it was verified.
