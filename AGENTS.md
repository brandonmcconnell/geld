# Geld — guide for agents and contributors

Geld is a browser extension that hides test files (and, optionally, other review noise) from GitHub diffs. This repository is a pnpm monorepo that also hosts the marketing site for geld.sh. Read this file before changing anything; it captures decisions that are not obvious from the code.

## Layout

```
packages/core/       @geld/core — pure TypeScript, no browser APIs. Glob matcher, hidden-file
                     categories & patterns, repository rules, settings model, unified-diff parser,
                     number formatting. Unit tested with Vitest. Consumed as TS source via
                     package.json "exports" (no build step).
apps/extension/      @geld/extension — the WXT extension (Chrome, Edge, Firefox, Safari).
apps/site/           @geld/site — Next.js site for geld.sh (see "Website" below).
assets/brand/        Logo + logomark SVGs (black and white variants). Both apps reference these.
.github/workflows/   CI: `pnpm check` (typecheck + tests everywhere), `pnpm catalog:check` (generated
                     catalog and its signature are current) and `pnpm zip:all` artifacts.
catalog/             patterns.json + patterns.sig: the signed pattern catalog installed extensions
                     fetch. Generated from core — never edit by hand (see "pattern catalog" below).
scripts/             catalog-build.ts (generate/check), catalog-sign.mjs, catalog-keygen.mjs.
```

Releases: every push to `main` that touches the extension (apps/extension, packages/core, assets/brand, the lockfile, or the workflow) publishes a GitHub Release from CI, tagged `v{version}-build.{run}` with one zip per browser plus `-sources.zip` for Firefox review, auto-generated notes (editable afterwards) and marked latest; the site's install buttons read `/releases/latest`. Bump `apps/extension/package.json` `version` for a new version number; the build number keeps tags unique. `workflow_dispatch` forces a release.

Commands (root): `pnpm check` (typecheck + tests for core and the extension, lint + production build of the site, and `catalog:check`), `pnpm test`, `pnpm build`, `pnpm zip:all` (zips for all four browsers into `apps/extension/.output/`), `pnpm dev` (extension), `pnpm dev:site`.

## Conventions

- TypeScript strict everywhere. **Never use `any`**, explicitly or implicitly, and never `ZodTypeAny`. Prefer type guards and `unknown` over casts; the codebase has no `as X` casts outside a couple of well-commented interop shims. Keep it that way.
- Extension imports shared logic only from `@geld/core` (never `../../packages/core/...`). Anything that could be reused by the site belongs in core; anything touching `browser.*`, the DOM or WXT stays in the extension.
- UI copy is short and specific; commit messages explain *why*.
- Website stack (fixed by the owner): latest stable Next.js (App Router, static generation; Cache Components/PPR for any dynamic bits), Tailwind, **shadcn on base-ui (not Radix)**, the **`cn` package** for class merging (not `clsx`, `tailwind-merge` or `cnfast`). Deployed on Vercel under the **dreamthinkbuild** account to **geld.sh** (canonical `www.geld.sh`, apex redirects).

## How the extension works (short)

- `apps/extension/entrypoints/github.content/` runs on github.com (and user-added GitHub Enterprise hosts). `src/github/controller.ts` is the brain: a debounced `MutationObserver` re-runs an idempotent `apply()` that classifies each diff entry with `@geld/core`'s matcher, hides matches with **CSS flex `order` + attributes** (GitHub's DOM is never moved — the React view breaks otherwise), rewrites header counts, renders the bottom "N files hidden" row, and turns the file-tree sidebar into a full-height accordion ("Changes" + one panel per hidden category).
- **Sidebar accordion** (`src/github/ui/tree-section.ts`, CSS section "Full-height accordion"). GitHub's sticky pane is marked `[data-geld-sidebar]` and becomes a flex column (or keeps its row direction, `data-geld-sidebar-layout`); the wrappers down to the tree are `[data-geld-sidebar-path]`; GitHub's `ul` (`[data-geld-tree-list]`) and the open Geld panel's list are the only scroll containers. Nothing about its size is written per scroll frame: the pane's height is the scroll-independent `100vh − sticky top` (stylesheet rule keyed on `--geld-sticky-top`, `!important` because GitHub's legacy `diff-layout` element rewrites the pane's inline height on every scroll), so once the pane is stuck its bottom is the viewport bottom, and before that it overhangs the fold. The headers below the open panel (`pinSidebarHeaders`, `[data-geld-pinned]`) are `position: sticky; bottom: <height of the headers beneath>` with an opaque background, so during the overhang the compositor keeps them on the viewport edge — no JS, no lag. That needs `overflow: visible` on the pane and every wrapper (sticky measures against the nearest scroll container), zero bottom padding and zero flex `row-gap` on them (a gap would be a see-through slit in the stack). The one scroll-dependent value is the overhang (`SidebarSizer`, rAF on scroll): it becomes an `::after` spacer (`--geld-overhang`) inside the open list so its last rows can still be scrolled above the headers; a frame of lag there is invisible because that area is covered. Padding would not do: it is part of the flex item's box and would push the list's end down, feeding back into the measurement. Narrow, non-sticky layouts (`stickyTopOf` returns null) keep GitHub's sizing and nothing is pinned.
- **Two layouts** (`settings.groupHidden`). Grouped (default): hidden entries are reordered to the bottom with CSS `order` behind the "N files hidden" row, and the sidebar becomes the accordion. Inline (`groupHidden: false`): nothing moves; hidden diffs are collapsed with GitHub's own control on every pass until the user clicks one (`inlineTouched`), the sidebar keeps GitHub's tree with hidden rows faded (`data-geld-tree-mode="inline"`) and their file icon swapped for the category icon. Adapters expose `expandEntry`/`collapseEntry`, which return `false` when the header has not rendered its control yet (rich diffs render in two steps).
- Two adapters read GitHub's DOM: `views/legacy.ts` (classic Turbo/web-components diff view) and `views/react.ts` (commit pages and the newer PR files experience). Selectors were verified live against github.com in Sep 2026; the signed-in React PR files view was verified only indirectly (same components as commit pages). GitHub Enterprise Server was not tested against a real instance.
- Line counts come from the page when it renders per-file diffs; otherwise (PR conversation tab, PR lists, partially loaded large PRs) the background fetches the same `.diff` GitHub serves, via `entrypoints/background.ts` (needed because github.com redirects to `patch-diff.githubusercontent.com` without CORS). Parsed diffs are cached in `storage.local` as `github:{owner}:{repo}:{pull}:{sha}` (`…:commit:{sha}` for commits; `github@{host}:` on Enterprise); writing a new SHA for the same pull drops the old one. **Header counts on PR/commit pages come only from that diff, never from the DOM**, so they change at most once (GitHub's number → ours); DOM totals are used only where no commit key exists (compare pages). The content script runs at `document_start` and rewrites the header synchronously inside the MutationObserver callback (before paint) whenever a settled or cached value exists, because GitHub's React header re-mounts several times while a page streams in. Rate limiting: four concurrent fetches, only for rows near the viewport, 60 s backoff on 429/403. **No GitHub API is used.**
- Browsers do not inject content scripts into tabs that were open before an install/update. `src/lib/inject.ts` puts Geld there on demand: the background injects into every open GitHub tab on `onInstalled`, into a GitHub tab on `tabs.onActivated` when it does not answer a ping, and when the popup gets no answer (`geld:ensure-content`, then one retry). The content script dispatches a `geld:takeover` event on start so an older copy still running in the page retires (and `ctx.onInvalidated` retires orphans), so there is never more than one active instance.
- Settings live in `storage.sync` (`src/lib/storage.ts`, writes serialised). Categories are opt-in except tests (and the user's own categories, which default on). Every built-in category has `groups` (off-switches per pattern group, keyed `category/group`) and `categoryPatterns` (extra lines incl. `!` rescues, scoped to that category); `customCategories` hold user-defined ones (`custom:<slug>` ids, title, Octicon name from `category-icons.ts`, patterns, optional nouns) and are matched first. Legacy `testGroups`/`customPatterns` migrate in `normalizeSettings`. Repo rules are gitignore-style (`owner/repo` off, `!` on, last match wins). Pattern lists support `[owner/repo]` scope headers.
- **The pattern catalog updates without a store release.** The built-in categories, their groups and globs are authored once, in TypeScript (`@geld/core/categories.ts` + `test-patterns.ts`), wrapped as `BUNDLED_CATALOG` (`Catalog` = `{ version, minExtensionVersion, categories }`). `pnpm catalog:build` generates `catalog/patterns.json` from it and `pnpm catalog:sign` writes `catalog/patterns.sig` (Ed25519 over the file's exact bytes, private key in the `GELD_CATALOG_PRIVATE_KEY` env var, held by the owner outside the repo; `pnpm catalog:keygen` prints a new pair, the public half lives in `catalog-key.ts`). CI runs `pnpm catalog:check`, which fails when the JSON drifted from the TypeScript or the signature no longer matches. **Publishing a catalog change:** edit the TS → bump `CATALOG_VERSION` (`YYYYMMDD`, or +1 for a second release that day; the build refuses a content change without a higher version) → `pnpm catalog:build` → `GELD_CATALOG_PRIVATE_KEY=… pnpm catalog:sign` → commit all three. Installed extensions pick it up within a day; **the site renders from the bundled TS, so it needs a deploy** (core changes trigger one on Vercel). **Ids are permanent:** settings and gists refer to `category` and `category/group` ids, so the build fails if an id from the previous committed `patterns.json` is missing — deprecate a group by emptying its `patterns`, never by deleting it; adding a *category* still needs an extension release (it needs a default, and `resolveCatalog` ignores categories the build does not know). **Trust model** (`@geld/core/catalog.ts`): the extension (`src/lib/catalog.ts`) fetches the two files from `api.github.com` (contents API, raw media type — already a host permission; `raw.githubusercontent.com` would need a new one and disable the extension in Chrome until re-approved) on install, on browser start (at most every 6 h) and via a daily `alarms` alarm, verifies the signature *before* parsing, validates the whole document (`parseCatalog`: shape, `[a-z][a-z0-9-]*` ids, known icons, every glob compiles), and stores it in `storage.local` (`local:catalog` = `{ version, fetchedAt, json }`) only if `minExtensionVersion` ≤ the manifest version (first three numeric parts) and `version` is higher than the active one. `resolveCatalog(bundled, fetched)` takes content (groups, globs, titles, descriptions, icons, nouns) from the fetched file and policy from the bundled one — `defaultEnabled` and the set of categories can only change in code, so a remote file can never turn a category on for everyone; groups are unioned so nothing a setting refers to disappears. A 403/429 backs off until GitHub's `x-ratelimit-reset` and is not shown as an error; every other outcome lands in `local:catalogStatus`, which the options page's "What to hide" card shows ("Built-in patterns (v…)" / "Patterns updated … (catalog …)", "Check now", last failure reason). `autoUpdatePatterns` (General, extension only) opts out; "Check now" still works. Everything that lists or matches built-in categories takes the catalog as an argument (`createMatcher`, `allCategories`, `categoryById`, `describeAdvancedSettings`, `validateSettingsDocument`, `readRemoteValidated`…), defaulting to `BUNDLED_CATALOG`; the content script, popup and options page `loadCatalog()` on start and `watchCatalog()` for changes. The pure parts (parse, verify, resolve, version compare) are in core and unit tested; only the fetch/cache/alarm wiring is in the extension.
- GitHub sign-in is the OAuth **device flow** (`src/lib/github-auth.ts`, no secret, no server); settings sync to a secret gist orchestrated by `src/lib/account-service.ts` in the background. Client id comes from `WXT_GITHUB_CLIENT_ID` (`.env`) or the options override; tokens live in `storage.local` only.
- **Settings are described once, in `@geld/core/settings-schema.ts`** (`SETTINGS_SCHEMA`): sections, fields (`toggle`, `categories` — switch plus an "Advanced" disclosure with group checkboxes and extra patterns, opened on load only when `hasAdvancedSettings` — `custom-categories`, `list`), copy, placeholders, a `popup` flag (also show in the toolbar popup) and optional `surfaces` (`extension` / `site`) for fields that only make sense in a browser (badge, shortcut, Enterprise hosts, which need permission prompts). The popup renders `fieldsFor('extension', true)`, the options page fills its cards (`data-section="…"`) from `sectionsFor('extension')`, and geld.sh renders `sectionsFor('site')`. Add a setting by extending `GeldSettings`, `DEFAULT_SETTINGS`, `normalizeSettings` and the schema — the schema test fails until every boolean/list key is covered. Copy may use `backticks`; render them with `splitInlineCode`.
- **The gist format is shared too:** `@geld/core/gist-sync.ts` owns the file name (`geld-settings.json`), the `{ geld: 1, savedAt, settings }` payload (also what Export/Import uses), `settingsEqual`, and the read/find/write calls. Read with `readRemoteValidated` wherever a person can be told about problems; `readRemote` is the lenient variant for code that only needs a best-effort value.
- **Hand-edited settings are validated, not silently repaired.** `@geld/core/settings-validate.ts` (`validateSettingsDocument`) scans the whole file and returns every issue with a path (`settings.categories.tests`, `settings.customCategories[1].icon`, line/column for JSON syntax via its own scanner). Unknown keys are ignored on purpose so a newer version's settings never look like corruption to an older one, and so are *well-formed* category/group ids the active catalog does not know (a gist may have been written against a newer catalog or a newer Geld); ids are still checked for shape and values for type, and `normalizeSettings` keeps such group keys rather than dropping them. When the gist is invalid the extension sets `syncState.remoteInvalid`, pauses sync both ways, and shows the alert whose copy is `CORRUPTED_SETTINGS_COPY` (Open gist / Reset to default settings / Check again); the site should render the same from `readRemoteValidated`. Reset writes `DEFAULT_SETTINGS` to the gist and this device. Rollback to a previous revision is left to the gist's own history rather than tracked by Geld.
- **Popup and options styling mirrors the site**, not GitHub: `src/ui/base.css` declares the same oklch tokens as `apps/site/app/globals.css` with `light-dark()`, bundles Geist/Geist Mono variable fonts (`src/ui/fonts/`, OFL), keeps everything square except buttons and the account control (`corner-shape: bevel square` on TL/BR, plain square where unsupported), and uses the site's 36×20 switch with a 12px thumb. Change a token in both places or not at all.
- **Safari ships through a thin Xcode wrapper** in `apps/extension/safari/` (generated once with `pnpm --filter @geld/extension safari:project`, i.e. `xcrun safari-web-extension-converter --copy-resources`; committed, including the copied extension build under the extension target's `Resources`). Before every App Store archive run `pnpm --filter @geld/extension safari:sync`: it rebuilds the Safari flavour, rsyncs it over `Resources`, sets `MARKETING_VERSION` from `package.json` and bumps `CURRENT_PROJECT_VERSION`. Archive/upload happens in Xcode (`safari:open`, Product → Archive, Distribute App → App Store Connect); submissions must come from a release Xcode, not a beta. Bundle ids `sh.geld.safari` / `sh.geld.safari.Extension`.
- Toolbar icon dark mode: Chrome/Edge use an offscreen `MATCH_MEDIA` document; Firefox uses `theme_icons`; Safari tints template icons. Icons are pixel-snapped renders of `assets/brand/geld-logomark.svg` (see git history for the generator approach; regenerate at 1/2/3 px per grid unit).

## Website (apps/site)

A small, fast marketing site for geld.sh, not a docs site. Run it with `pnpm --filter @geld/site dev` (or `pnpm dev:site`); `pnpm --filter @geld/site check` runs typecheck, lint, unit tests and a production build, and is part of root `pnpm check`.

- **Stack:** Next.js 16 App Router with `cacheComponents: true`, Tailwind CSS 4, shadcn components generated on **Base UI** (`components/ui/`), the `cn` package for class merging, Geist via the `geist` package, `lucide-react` icons. Everything is prerendered; the only cached-async piece is the latest-release lookup (`lib/release.ts`, `use cache`, revalidated hourly, falls back to the Releases page when there is no release yet). Light/dark follows `prefers-color-scheme` by default; the footer's theme menu (`components/theme-menu.tsx`, `lib/theme.ts`) can pin a scheme via `data-theme` on `<html>`, persisted in localStorage and applied by an inline script before paint. Colour tokens use `light-dark()` keyed on `color-scheme`, and the `dark:` variant covers both cases (globals.css). Nothing on the site is rounded except the GitHub-imitating demo visuals (kept round on purpose). Calls to action — buttons, button-like links, clickable pills — use the `geld-corners` utility: square with the top-left and bottom-right corners cut via `corner-shape: bevel square` (size from `--geld-cut`, `geld-cut-*`), echoing the logomark; hover deepens the cut by 3px (a child inside `group/geld`, like the account avatar, follows its parent's hover), and an `::after` pseudo-element makes the hit area the full square plus 1px so the cut-away corners are still clickable. Browsers without `corner-shape` get plain square corners. Form fields, chips, cards, popups and badges are plain squares. Hover details that phones must reach (the count breakdowns) use `components/ui/popover.tsx` (opens on hover and tap), not the tooltip. The white brand SVGs are shown in dark mode by toggling two `<img>`s with that variant (`components/logo.tsx` references `assets/brand/` via `new URL(..., import.meta.url)`); the SVG favicon can only follow the OS.
- **Pages:** `/` (hero, before/after PR header + hidden row built from `components/demo/sample-pr.ts`, which classifies its sample files with `createMatcher(DEFAULT_SETTINGS)` so the picture cannot lie; install buttons; live "try a path" demo in `components/path-tester.tsx`), `/how-it-works`, `/patterns` (rendered from `CATEGORIES` — the same source `catalog/patterns.json` is generated from — never hand-written; no runtime fetch, so a catalog change reaches the site with the next deploy), `/faq`, `/privacy` (doubles as the store privacy policy). Favicons are drawn from the brand SVGs at build time (`lib/brand.ts`); the OG image (`app/opengraph-image.tsx`) combines the wordmark with a real 2× screenshot from `assets/screenshots/` (embedded as a data URL, `loadScreenshot`). Re-capture that screenshot with the extension on a public PR when the header UI changes; the Vercel ignore script watches the folder.
- **Data that must stay in sync with the extension:** the version comes from `apps/extension/package.json` (`lib/version.ts`); patterns and categories from `@geld/core`; install links from the latest GitHub Release until store listings exist — set a URL in `STORE_URLS` (`lib/downloads.ts`) to switch a browser over. Author profile URLs live in `lib/site.ts` (entries with `url: null` are not rendered).
- **Deployment:** Vercel, dreamthinkbuild account, Root Directory `apps/site`, domain geld.sh. `apps/site/vercel.json` points the Ignored Build Step at `scripts/vercel-ignore.sh`, which skips builds for commits that only touch the extension (core, the extension's `package.json`, brand assets and the lockfile do trigger builds).
- **No database, ever.** The only user data is the settings gist on the user's own GitHub account. The site signs users in with the **same OAuth App** as the extension, via the web flow (the App's callback URL is `https://www.geld.sh/auth`; the extension's device flow never uses it). The canonical host is **www.geld.sh** (`SITE_URL`); the apex 308-redirects to it. `callbackOrigin()` returns the same origin as `authOrigin()` and must match the App's registered callback exactly. Code: `app/auth/start` (state cookie + redirect to GitHub), `app/auth` (callback: verify state, exchange code, `fetchGitHubProfile`, set cookie), `app/auth/signout` (POST: clear + best-effort revoke), `app/auth/expired` (pages redirect here on `SignedOutError` because only routes/actions may write cookies). `lib/auth/config.ts` reads `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `AUTH_SECRET` (all server-only; `AUTH_SECRET` derives the AES-GCM key in `lib/auth/crypto.ts`) and the redirect origin comes from `authOrigin()` — `http://localhost:3000` in development, `SITE_URL` otherwise, never from request headers. The `gist`-scoped token lives only in the encrypted HttpOnly `geld_session` cookie; a readable `geld_account` cookie carries login + avatar for the header. `/settings` renders `sectionsFor('site')` and reads/writes the gist with `@geld/core/gist-sync` through server actions (`app/settings/actions.ts`) that re-read the gist (strictly, via `readRemoteValidated`) before layering a change on it; an `invalid` gist renders the shared `CORRUPTED_SETTINGS_COPY` alert (`components/settings/corrupted-settings.tsx`) with the issue list, an Open gist link and a reset-to-defaults action instead of the form, and saves are refused until it is fixed. The site accepts no uploaded files today; if it ever does, run them through `validateSettingsDocument`. `/auth*` and `/settings` are dynamic; everything else stays prerendered.
- **Auth environments.** Production has the three env vars in Vercel. **Preview deployments deliberately have none** (an OAuth App accepts one callback host) and `authConfig()` additionally returns `null` whenever `VERCEL_ENV` is not `production`, so `/settings` shows "Sign-in isn't configured in this environment" and the build still succeeds. Local development needs a *second* OAuth App whose callback is `http://localhost:3000/auth`; put its values in `apps/site/.env.local` (see `.env.example`). Without real credentials the flow can be exercised against a fetch mock, which is how it was verified.

## Verifying changes

There is no GitHub login available to automation here. Verify against public pages: `https://github.com/wxt-dev/wxt/pull/2544/files` (classic view, 6 test files), `https://github.com/wxt-dev/wxt/commit/d05ac55ba78b7d01c5ab9feb0e862775e45509ef` (React view), `https://github.com/vitest-dev/vitest/pull/10554/files` (124 files, progressive loading), `https://github.com/wxt-dev/wxt/pulls` (PR list). Branded Chrome ignores `--load-extension`; install the built folder with Puppeteer's `browser.installExtension()` and `--enable-unsafe-extension-debugging`, and bring a tab to the front before interacting with it (background tabs stall element handles).
